Session identity and storage layout

SessionManager is the application-facing facade; SessionStorage owns a lazily connected SQLx SQLite pool. The database lives under the configured data directory at sessions/sessions.db. Session state includes working directory, provider/model configuration, mode, extension data, optional recipe, archive/project metadata, and parent_session_id for delegation. Conversation loading is optional so metadata-only operations can avoid reading all messages.

The message table’s integer primary key and optional logical message ID have different purposes. Logical IDs correlate live updates and metadata; SQL row identity is storage machinery. JSON content preserves typed blocks beyond what role/text columns could represent. Inventory tables are also created during initialization; this table summarizes conversation persistence rather than the complete database.

Why BEGIN IMMEDIATE is a strong choice

A deferred SQLite transaction can read under a shared lock and later attempt to upgrade to a writer while another transaction is doing the same. Goose starts relevant write paths with BEGIN IMMEDIATE, taking the write reservation before performing their reads. With WAL and a 30-second busy timeout, contention is serialized at the start of the transaction rather than emerging as an awkward lock-upgrade failure midway through a read-modify-write sequence.

Schema creation uses that same approach and idempotent CREATE TABLE IF NOT EXISTS / INSERT OR IGNORE statements. A per-instance OnceCell prevents repeated initialization in one manager, while the SQLite transaction handles separate manager instances racing on first boot. A local once flag alone could not solve a cross-instance initialization race.

Persistence before an immediately answerable notification

The concrete effect handler ensures IDs and enriches usage, then applies each effect. Only after that pass does it publish tool-confirmation messages and usage/history events. A fast client can therefore answer an approval request without beating the database write that makes the request discoverable. This is a small ordering rule with a large behavioral impact.

Several effects can still involve separate storage calls and transactions. A tool can finish outside SQLite before its result is appended. A process crash at that point can leave the conversation with an unanswered request even though the external effect occurred. Recoverable conversation state is valuable, but exactly-once external mutation would require idempotency or a stronger application protocol beyond this handler.

Usage accounting is not prompt size

Session metrics distinguish latest request usage, accumulated usage, and ledger entries; cache read/write tokens are explicit. Compaction writes its own usage entries and computes retained context separately. Cost has a source marker because provider accounting and locally derived estimates differ. Export, import, copy, truncation, and metadata updates sit above storage and must preserve those meanings.

Metadata updates and secure local files

Tool-request patches find the request by call ID and merge into tool_meta under a write transaction. Message visibility changes use a logical message ID. Configuration uses separate file locking and secret storage; it is not another table in the conversation database. On Unix, session directory creation applies mode 0700. These choices reduce local accidental disclosure but do not make arbitrary tool outputs safe to expose or export.
