Discovery and the namespace contract

The extension manager lists tools, follows pagination, annotates ownership, and normally exposes extension__tool names. Selected first-class platform extensions expose unprefixed tools. Ownership metadata supports routing those names. Names shown to a model must map back to the intended server and its native tool name; blindly splitting every name on a separator is insufficient.

Tool names are checked for duplicates when the generic machine assembles inference input. Goose also records what was advertised for an inference message. A later request is eligible for execution only if it belongs to that advertisement or falls under the explicit compatibility behavior for messages without inference metadata. This links dispatch to the capabilities the model actually saw.

A cache that detects invalidation during fetch

Discovery can await slow MCP servers. Holding the cache mutex over those network calls would serialize unrelated work. Goose reads the cache under a short lock, captures a generation, fetches outside the lock, and only installs the result if the generation is unchanged and no other caller already filled the cache. Extension changes invalidate the cache and bump that generation.

The returned value can still reflect the fetch already performed during an invalidation race; the generation check prevents stale shared cache installation. It is a useful consistency compromise, not a linearizable discovery snapshot or a single-flight guarantee. Concurrent misses can duplicate discovery calls.

Pending requests and dispatch lifecycle

  1. Scan the kickoff suffix for tool requests and matching tool responses, excluding answered and externally executed calls.
  2. Reconstruct approval state and inspect advertised pending calls; mark executable decisions or persist an ActionRequired request.
  3. Filter pending requests against current known tools. Chat mode returns a skipped-tool result instead of dispatching.
  4. For executable calls, run blocking pre-tool hooks, collect extended observations, and dispatch with session and cancellation context.
  5. Merge result/notification streams, correlate by tool ID, emit post-tool success or failure hooks, and persist results.
  6. Unknown-tool handling provides a separate resolution path for calls current operations cannot dispatch.

A tool result marked is_error=true is a failure even if the transport returned Ok. That classification is shared with recipe final-output execution so policy does not silently depend on which path invoked the tool.

Code mode: tools as program callbacks

The optional code_execution platform extension builds PCTX callbacks from model-visible tools, excluding itself and resource-only entries. Public names are decomposed into namespace/function pairs using separators or owner metadata. Programs can combine calls and process intermediate data inside a JavaScript runtime rather than returning every intermediate value to the model.

Callback configuration is serialized, sorted, and hashed so discovery order does not trigger pointless rebuilds. The cache uses read-then-write double checking. Runtime execution runs on a blocking worker with a current-thread Tokio runtime; native async callbacks bridge back to the main runtime. Timeout and cancellation cancel dispatch and briefly drain the task before returning.

Resources and prompts are first-class capabilities

MCP extensions can expose resources, reusable prompts, and tool-linked UI resources as well as tools. Goose’s manager provides list/read/get operations and MCP Apps attachment handling. Dynamic extension changes mean history can refer to a server that is no longer active; prompt assembly explicitly tells the model which extensions are currently available and sorts them to stabilize the prompt cache.
