A message is richer than a chat string

The internal Message contains a role, creation time, content blocks, optional stable ID, metadata, and other typed state. Content includes text, image, document, tool request/response, reasoning, redacted reasoning, action-required, notifications, and errors. Tool requests carry a correlation ID and a Result-valued parsed call; a malformed model call is representable without pretending it is executable.

Roles and effective roles

MCP’s role enum supplies User and Assistant, but tool results are represented in user-role messages. The conversation layer derives an EffectiveRole to distinguish tool responses from new user input. Agent predicates rely on that distinction to know whether to call inference, execute tools, or finish. Directly counting user-role messages produces the wrong answer for a tool-heavy task.

ToolRequest and ToolResponse are paired by their ID, not by array position. An assistant can request several tools, and notifications or approvals can appear between the request and result. One ID is the unit of unanswered-work detection, approval state, external execution tracking, and metadata patching.

Two visibility axes and content audiences

Projection Meaning Examples
User visible Belongs in the displayed transcript Original user prompt, public assistant text, tool status.
Agent visible Belongs in the next model request User prompt, tool response, hidden compaction summary.
User only Displayed without feeding it back Some approval prompts and command responses.
Agent only Model context without visible chat noise Compaction continuation and goal nudge.

A message-level flag alone is insufficient: individual TextContent blocks can have audience annotations. agent_visible_messages filters metadata, then projects content and drops empty messages. The user projection does the analogous operation. A message that contains both public and private blocks must not flatten them into a single unannotated string.

Streaming coalescence

Conversation::push coalesces fragments only when the incoming and trailing messages have the same nonempty ID; otherwise it appends a message. Text merging preserves audience boundaries. Thinking blocks can merge while the preceding block is unsigned, or when signatures match. A signed block followed by an unsigned delta starts a new block. Multi-block incoming chunks do not enter the single-block thinking merge case. These conditions preserve provider-issued signatures and semantic boundaries.

The completion collector has matching rules. Its output uses the last supplied usage report; it does not sum reports. Missing usage with a message produces default usage for model “unknown.” Usage without a message yields an empty assistant message. An entirely empty stream returns ExecutionError. Consumers must distinguish these cases instead of assuming every success contains text.

Events and serialization are separate surfaces

AgentEvent is an internal Rust event enum. ACP handlers translate it into standard session updates and Goose custom notifications; it should not be treated as the JSON-RPC wire schema. Goose custom requests generally serialize fields as camelCase, while extension configuration uses a tagged snake_case type discriminator. The serialization attributes in each type are authoritative.

Conversation repair preserves a requestable history

The conversation module includes fixes for protocol-invalid sequencing and separate merging for outgoing requests. The persisted transcript can retain visibility boundaries that a provider-specific request needs to collapse for role alternation. Request normalization is a view of history, not permission to overwrite the history itself. This separation makes provider format constraints compatible with audit-friendly local records.
