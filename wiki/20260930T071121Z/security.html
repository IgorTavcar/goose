Modes and decisions

Mode is one input to policy, not the entire security mechanism. Tool inspectors can allow, deny, or require approval with a warning. Permissions include one-time and persistent allow/deny choices and cancellation. The state machine persists executability and reconstructs confirmations from messages, so an approval reply is an input to a durable decision rather than an untracked UI action.

Inspector composition is restrictive

The default manager registers security, egress, adversary, permission, and repetition inspectors. Enabled inspectors run in registration order and contribute findings. Deny removes a request from approved and needs-approval lists. RequireApproval removes it from approved and only adds it if it has not been denied. Allow does not override an earlier restriction. This is a useful monotonic policy composition: later permissive evidence cannot weaken a stricter decision.

The inspection coordinator logs an individual inspector error and continues. Therefore the coordinator itself is not globally fail-closed on every inspector exception. Each inspector’s actual detection and failure semantics must be reviewed separately; the presence of an “adversary” or “security” component is not a proof that all hostile prompts are detected.

Approval reconstruction algorithm

ApprovalState scans the kickoff suffix, building sets of answered call IDs and confirmation requests plus a map of confirmation responses. Pending approval candidates exclude answered requests, already requested/answered confirmations, externally executed calls, nonexecutable calls, parse errors, and calls not in the advertised capability set. A response is applicable only while the underlying tool request is still unanswered.

The matching key is the tool-call ID. A client that resends a decision after cancellation or completion must not create a fresh execution merely by producing another user-role message. Persisted executability and confirmation bookkeeping make that distinction inspectable.

Hooks: vetoes versus observations

PreToolUse is a blocking policy chain; a denial returns a tool error before execution. PreToolUseResult observes the chosen outcome and has no veto. PostToolUse or PostToolUseFailure fires according to both transport success and the result’s is_error flag. Extended shell/file events add matcher context. Stop hooks can request continued work, bounded by a configured cap so hooks do not create an unbounded finish loop.

Sharing lifecycle helpers between ordinary extension tools and recipe final-output execution avoids separate policy semantics for two execution paths. Observational callbacks are best effort and should not be assumed to prove successful external logging.

ACP transport authentication and origins

The standalone transport supports a secret in X-Secret-Key or a token query parameter. The comparison uses subtle::ConstantTimeEq for candidate bytes. The router selects an origin policy based on configured allowed origins and whether token auth is required. Health/status endpoints are auxiliary routes; their success is not evidence that ACP authentication or a provider request succeeds.

A transport credential authorizes access to a backend; it is distinct from per-tool approval. Desktop also verifies TLS readiness fingerprints in its backend startup path and keeps nodeIntegration off with contextIsolation on. Those controls concern frontend/backend trust, not a sandbox around every shell tool.

Extension environments, telemetry, and roaming

Envs rejects a curated set of process-manipulation variables such as PATH and loader injection settings when constructing extension environment configuration. Secrets can come from environment, system keyring, or a private secrets file. The SDK observability hook defaults payload capture off because system prompts and conversations can contain sensitive data. Enabling capture changes that disclosure boundary.

Roaming uses authenticated peer keys and a trust book rather than possession of a connection card. A card contains public identity and reachability information; accepting a peer grants the full ACP surface described by that transport. Revocation reload failure is documented as fail-closed. This is a different trust model from the local HTTP bearer secret.
