Local ownership and replaceable intelligence

The project presents Goose as a general-purpose agent running on the user’s machine, with desktop, CLI, and embedding surfaces. The same task machinery can work with multiple model providers and MCP extensions. Its philosophy, as inferred from that implementation, is to keep the agent’s orchestration and tools in an open runtime while allowing the source of intelligence to vary.

Local execution does not mean every request stays offline. Native cloud providers send model requests to external services; remote extensions and ACP providers introduce their own boundaries. On-device inference is a distinct optional implementation. The architectural freedom lies in selecting those boundaries rather than hiding them.

A small kernel with explicit policy

The generic state machine owns ordered dispatch, effect identity, cancellation checks, and the reload/apply loop. It does not own Goose’s recipe model, permission settings, or SQL schema. Concrete operations contribute tools and prompt parts and return effects. This keeps “when does this behavior apply?” near the behavior itself, while the kernel remains reusable.

The cost is ordering sensitivity. The first applicable operation wins. Moving compaction, approval, or turn limits can alter behavior even if each operation’s code is unchanged. Composition order therefore belongs to the specification and deserves review alongside operation implementations.

The conversation is both evidence and control state

State-machine decisions are largely reconstructed from history. Approval requests, confirmations, tool replies, errors, and operation notes make progress observable after rebuilding a pipeline. Notes record past actions, such as retry counts, rather than values an operation can compute again. This avoids a private loop counter becoming the only explanation of why the machine continued.

This is conversation-derived control, not deterministic replay of external effects. Provider calls are nondeterministic; tools can mutate the world before their result is stored; runtime configuration and queues can change. Persisting an operation note improves recoverability but does not turn the entire process into a transactional workflow engine.

Human history and model context are different products

A human needs an intelligible record of what happened. A model needs a bounded request that fits its protocol and context limit. Goose keeps user-visible and agent-visible projections, with content-level audience annotations as well as message-level metadata. Full compaction hides old history from the agent without erasing the transcript shown to the user, then adds a hidden summary and continuation.

That design permits a long-running session to remain inspectable after compaction. It also makes visibility rules consequential: an implementation that concatenates all text can expose private reasoning or feed display-only notifications back into the model. The projection helpers are semantic boundaries, not cosmetic filters.

Contracts instead of vendor assumptions

Providers share a streaming contract and normalized error enum. Model discovery and canonical metadata handle names and capabilities that vary by service. Declarative providers reuse existing engines for compatible endpoints, avoiding a separate handwritten adapter for each brand. The tradeoff is that compatibility remains a live service property: a JSON definition alone cannot prove that a backend accepts tools or follows a wire format.

The project’s release manifest distinguishes the published GDK set from internal application APIs. Public Rust visibility inside goose should not be confused with a stable embedding contract; custom ACP methods are explicitly marked unstable in their namespace.

Engineering values visible in contribution rules

Repository instructions favor explicit types, straightforward errors, self-explanatory names, and comments that explain unusual logic. They also require parity during the loop migration. These rules support a design where subtle behaviors—signed reasoning boundaries, write-lock timing, cancellation cleanup—are documented where they matter, while ordinary getters and constructors stay simple.

The evaluative words in this wiki, including “brilliant,” are editorial judgments based on inspected code. They are not benchmark results or upstream marketing claims.
