Recipe schema and execution intent

A recipe is a YAML or JSON task definition. Its version defaults to 1.0.0; title and description identify it, and at least instructions or prompt is expected. Optional extensions, model/provider settings, activities, author, parameters, structured response, sub_recipes, and retry configuration shape execution. A recipe packages inputs and policy; it is not a guarantee that the model will follow every instruction or produce a valid result.

Parsing and parameter validation

The recipe path performs template preparation, parses YAML or JSON, deserializes typed values, and validates parameters. The validation module defines limits of 32 parameters, 200 total select options, and 128 KiB serialized parameter data. Error formatting traverses a safe schema path rather than indiscriminately echoing arbitrary user-controlled map keys. Invalid syntax and invalid typed schema produce different errors.

Subrecipe values that arrive as numbers or objects are serialized into strings; plain strings retain their text. That makes downstream substitution consistent, but it means a caller must distinguish a string containing JSON from an already typed object. Use the checked-in validation and conversion paths rather than recreating them in a UI.

Recipe completion and retry algorithm

RetryOperation applies after a trailing assistant response satisfies ends_turn. A goal can add one hidden “verify the goal” nudge, recorded through operation metadata. A grind goal keeps adding continuation until another bound such as max_turns stops it. These nudges are not an independent proof of task success; recipe success checks supply concrete runtime validation.

  1. Run configured success checks under the configured timeout. Success allows later finish operations to proceed.
  2. Read retry attempts from the kickoff message. If the limit is reached, append an error.
  3. Optionally run the on_failure command under a separate timeout.
  4. Reset history to everything through the kickoff message and increment attempts on that retained message.
  5. Return a replacement-conversation effect so the next pass reattempts the task.

Putting the counter on the kickoff is a particularly strong detail: the reset deletes the failed attempt’s later messages, so a counter attached to its final response would disappear. These retries differ from provider network retries and can involve shell checks or cleanup commands.

Skills and project instructions

Skills add reusable task instructions and capabilities, while hints/project operations feed repository context into prompt preparation. Subdirectory hints are inferred from tool argument paths, enabling guidance relevant to the directories the agent has touched. The generic machine lets these operations contribute prompt parts independently of whether their run method applies on a particular pass.

Prompt parts should have stable order and defined identities because provider caching depends on prefix stability. A tool that moves into a new directory can legitimately change context without requiring every project instruction to be loaded from the beginning.

Delegation is session management with authorization

The orchestrator platform extension can list/view sessions, start an agent, send messages, and interrupt. New tasks inherit provider/model settings through the current session and use AgentManager. parent_session_id and SessionType distinguish delegated sessions from ordinary user sessions. Cancellation registration has a guard to remove a token when an incomplete setup exits.

The send-message authorization permits ordinary callers according to its non-SubAgent path, but restricts SubAgent callers to sibling delegated sessions with the same parent and rejects sending to oneself. A delegated task cannot use that operation to send into another tree, its parent user session, or a descendant merely because it knows the ID. These checks live in code rather than being left to prompt instructions.

Scheduling and reproducibility

Scheduler support stores and triggers recipe work with configured timing and service lifecycle. CLI commands and ACP custom schedule methods expose administration. Reproducibility depends on the recipe and values, selected provider/model, active tools, working directory, policy configuration, and the external state being acted upon. Saving a YAML file alone does not capture all of those variables.
