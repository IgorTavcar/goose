The system in one view

Goose is a local agent application and a set of embeddable Rust libraries. A client supplies a conversation; an agent selects operations and obtains model completions; tools perform work; session storage records the resulting history. The language model proposes actions, while runtime code controls capability discovery, approval, dispatch, cancellation, and persistence.

Two agent implementations coexist

The legacy implementation remains in agents/agent.rs. The newer concrete pipeline is assembled there but uses the reusable machine from goose-agent. The environment gate accepts 1, true, TRUE, or yes; its default is false. At the reply API, the selected path is passed explicitly as use_state_machine. This distinction matters when tracing callers: a boolean argument and the environment helper are separate pieces of the selection mechanism.

The repository requires behavior changes to be implemented and tested in both loops during migration. A reader should not infer that every feature has already moved to the state machine, or that a generic GDK operation is identical to a Goose application operation.

Ports, adapters, and dependency direction

The small crates define contracts; larger crates supply policies and adapters. MachineSession exposes an ID and optional conversation. SessionLoader and EffectHandler connect the machine to a runtime. Goose implements those traits on its SQLite-backed SessionManager. Provider implementations depend on message contracts rather than requiring a full desktop or CLI. This is a ports-and-adapters reading of the code, not a claim that the repository uses that name.

ACP and MCP occupy different edges. ACP exposes an agent to a user-facing client and streams updates back. MCP exposes tools, resources, and prompts to the agent. A remote ACP-backed provider adds another arrangement: Goose can act as a client of a separate agent harness instead of directly calling a model HTTP endpoint.

One request, end to end

  1. The frontend initializes an ACP connection or the CLI constructs a session and agent.
  2. Session configuration selects a provider, model, working directory, extensions, mode, and optional recipe.
  3. The incoming message is assigned a stable identity and persisted. The selected loop prepares model-visible history and current capabilities.
  4. Inference streams text and assembled tool requests. Approval and tool operations process unanswered calls.
  5. Tool results are correlated by call ID, effects update durable state, and another model turn can consume the results.
  6. Completion, a turn limit, an error, approval waiting, or cancellation returns control to the client.
